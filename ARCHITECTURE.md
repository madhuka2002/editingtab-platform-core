# EditingTab Platform Architecture

## Purpose

EditingTab is a modular tourism operations platform made of independently deployable products. This document defines the system boundaries that Platform Core must preserve.

The current repository is in an early foundation phase. Existing code provides a FastAPI application, an asynchronous PostgreSQL connection, an organization model and migration, and a health endpoint. The ownership below describes the intended boundary; it does not imply that every capability has already been implemented.

## Product Topology

Current and planned repositories are:

- `editingtab-platform-core`
- `editingtab-booking`
- `editingtab-social`
- `editingtab-chatbot`
- `editingtab-pos`
- `editingtab-notification`
- `editingtab-contracts`
- `editingtab-platform-docs`

Every primary product module must be independently deployable, independently usable, and independently maintainable. Optional modules must be safe to remove, leave unpurchased, fail, or place into maintenance without preventing unrelated modules from operating.

Services own their data. Cross-module behavior must use explicit versioned APIs, events, or connectors. A service must never directly read or write another service's database, share tables with it, or rely on database-level coupling. Shared message and API contracts belong in `editingtab-contracts`; platform-wide documentation belongs in `editingtab-platform-docs` when those repositories are available.

## Platform Core Boundary

Platform Core is the platform control plane. It owns only:

- organizations
- users
- organization membership
- authentication
- roles and permissions
- module entitlements and licensing
- integration metadata, but not product-owned integration data or workflows
- sessions and refresh tokens
- audit logs
- service identity
- platform Super Admin capabilities

Platform Core must not own or implement:

- hotel rooms or room availability
- bookings, reservations, or booking holds
- OTA synchronization
- social messages
- chatbot knowledge
- POS products or orders

These capabilities and their persistent data belong to their respective product services. In particular, Booking runs from a separate repository and uses a separate PostgreSQL database. Platform Core may authenticate a caller or communicate Booking entitlement information through an explicit contract; it must not become Booking's data layer or runtime dependency for unrelated local operations.

## Backend Architecture

The backend stack is Python, FastAPI, PostgreSQL, SQLAlchemy 2.x, asyncpg, Alembic, and pytest. PostgreSQL is authoritative for persistent state.

Code must follow this dependency direction:

```text
API -> Service -> Repository -> Database
```

- API handlers validate transport input, invoke services, and translate results to HTTP responses.
- Services implement use cases, authorization decisions, and transaction-level orchestration.
- Repositories encapsulate persistence queries and mapping.
- Database infrastructure provides asynchronous sessions and PostgreSQL access.

Do not put database access in API route handlers. Database operations must be asynchronous and parameterized through SQLAlchemy or an equivalent safe database interface.

## Multi-Tenancy and Security

This is a production multi-tenant system. Every operation on tenant-owned data must derive and enforce the organization boundary server-side. Client-supplied organization IDs, user IDs, roles, permissions, or entitlements are claims to validate, not authority to trust.

Authentication and authorization are server-side responsibilities. Validate all incoming data, keep credentials out of source control and logs, and make high-risk operations auditable. Logs must not contain passwords, secrets, access tokens, refresh tokens, or full third-party credentials.

Service-to-service calls must use an explicit service identity and narrowly scoped authorization. Integrations should fail within their own boundary, use timeouts and observable error handling, and avoid making optional services a hidden availability dependency.

## Data and Schema Evolution

Each service evolves its own schema with its own migrations. In Platform Core, every schema change uses Alembic. Autogenerated revisions must be reviewed, explicit column constraints and defaults must be chosen deliberately, and downgrades should be valid where practical. An already-shared migration is immutable unless an explicit instruction authorizes otherwise.

## Delivery Principle

The immediate business objective is a sellable Booking V1 within 40 days. Platform Core work must stop at the minimum secure control-plane capability Booking needs: organizations, users, secure authentication, organization membership, basic RBAC, and sufficient module entitlement support. Additional Core sophistication is deferred unless it blocks that objective or is explicitly prioritized.
